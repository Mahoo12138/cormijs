# Cormi MVP 开发与验证计划

版本：Draft 0.6。修订日期：2026-10-16。

本计划以 [架构设计](02-architecture.md) 为边界，以 [源码研究](01-source-study.md) 中的固定提交为参考。**本轮开始 P0 实现，不代表整个 P0 或 P1 已通过。** 每项实际验证结果单独记录；设计目标、已实现和已测试必须分开。参考仓库不安装依赖、不修改。

## 1. 开发顺序与成功定义

第一版的成功不是“启动后出现一个 React 页面”，而是一个新的应用能够通过配置和 preset 获得可解释的路由、构建和开发更新；插件依赖不满足时能明确失败；连续修改文件不会提交过期产物；退出和配置重启不遗留 watcher、端口或子进程。

推荐按 **P0 关键假设验证 → P1 可用纵切 → P2 开发态可靠性 → P3 发布前稳定化** 推进。阶段按退出条件划分，不按先验的人月数划分。没有对当前依赖和集成做实验之前，不沿用此前研究中确定性的工期估计。

现阶段不要同时启动 SSR、微前端和兼容 Umi 插件等支线。每个阶段只交付能独立评审的完整链路，不提前创建大量空包、空 service 和无法运行的示例。

## 2. P0：验证内核与集成假设

P0 的产物应是小型实验、自动断言和结论记录，而不是未来框架的半成品架构。建议在实现开始后建立 `tests/spikes/`，只安装这些实验实际需要的依赖，不在两个上游 monorepo 中直接安装全部依赖。

### P0-A：Cordis 就绪与失败传播

创建 provider、consumer 和一个测试宿主，分别覆盖 provider 先注册、consumer 先注册、provider 永远不存在、provider 异步失败、consumer 初始化期间被 dispose、父插件同时提供服务与等待子插件等情况。

要观测的不是单个 Promise 是否 resolve，而是插件最终 state、apply 次数、服务实际可用性、所有初始化与清理任务是否结束。专门证明当前版本 `await ctx.plugin()` 对 PENDING 的行为，并据此实现 `awaitRequiredPlugins()` 的适配策略。

退出条件：缺失依赖不能假装启动成功；初始化失败有原始 cause；没有无期限等待；同一次插件激活不能被误报为多次；父子依赖的危险组合要么预检拒绝，要么以有界超时和依赖链诊断终止。

### P0-B：受管副作用与关闭顺序

创建一个真实临时目录 watcher 和一个占用临时端口的测试服务，让 consumer 在清理期间继续读取 provider；随后分别卸载 consumer、provider、父插件和根上下文。加入延迟清理、清理抛错、初始化中途失败及未结束 Promise。

不要假设所有 disposer 全局串行。将有先后关系的清理放在同一个 owner 中，并记录 timeline。验证 Cordis 根 Fiber dispose 后的行为，确保 Cormi 自己的 ProjectRuntime 在 dispose 后不能被意外继续使用。

退出条件：正常清理后临时端口可重新绑定，watcher 不再收到事件，consumer 清理时所依赖资源仍符合契约。清理异常必须出现在宿主诊断和最终退出结果中；故障隔离超时不能误杀其他项目的进程。

### P0-C：编译扩展点与确定性

实现最小 `series / reduce / collect`，验证前后顺序、重复 hook ID、缺失顺序目标、顺序环、返回非法值和异步异常。使用相同输入但不同的异步完成顺序重复执行，最终路由和 runtime 清单必须一致。

退出条件：输出只由输入与声明顺序决定；错误包含 pluginId、hookId 和 phase；编译中的注册/注销不能改变已封闭快照。这个模块只管理编译回调，不复制 Cordis 的服务容器。

### P0-D：可替换 builder 与 Vite 会话

用一个固定 HTML/TSX 入口验证 dev、build、preview 和关闭行为。加入端口被占用、启动途中失败、不同项目的 dev/build 独立运行，以及同一项目 dev 持锁时尝试 build 的场景；最后一种必须在写入前报告 PROJECT_BUSY。所有运行必须使用锁定版本，不依赖两个上游仓库的间接依赖碰巧可用。

退出条件：同一个临时端口能连续创建与关闭会话；每次 build 都能结束进程；生产和开发环境不会相互污染；返回的实际关闭接口与 adapter 一致。特别验证 `configureServer` 的后置回调没有被误用为 disposer。

增加三个独立验收：core 在未安装 Vite 的消费者目录中可运行；同一个 Web consumer 改用测试 builder 后不改代码；Vite provider 在启动中卸载、关闭失败和重复启停时不遗留资源。测试替身只证明契约边界，不证明 Rspack/Webpack 的兼容性。worker 隔离和同项目写锁仍是后续独立退出条件，不因单进程实验通过而标为完成。

### P0-E：版本与环境基线

首次研究时 Runner 默认 PATH 无法找到 Node；本轮已定位现有 `/Users/mahoo/.nvm/versions/node/v22.14.0/bin`，使用 Node 22.14.0 与 pnpm 10.6.3。仅为执行子进程设置 PATH，没有修改全局 shell 配置。项目 `.nvmrc` 记录实验版本。

记录 Node、包管理器、Cordis、Vite、React、React Router、TypeScript 的精确版本，以及运行平台。核实 Cordis RC 的可用发布产物与源码是否一致；不能仅凭包内版本字段认定 npm 发布状态。Node 22.12+ 是设计候选，最终支持范围以实际依赖交集和测试结果为准。

P0 至少在主开发 Mac 和 Linux CI 跑通；Windows 路径及进程退出测试应在承诺支持 Windows 前完成。若 RC 某项关键行为不满足契约，优先缩小能力、固定经过测试的版本或封装小型适配，而不是静默依赖内部实现。

## 3. P1：一个真正可用的应用纵切

P1 按一个可执行链路开发：CLI 读取配置 → 展开 React preset → 创建 Cordis 宿主 → 形成路由与 runtime 清单 → 生成入口 → Vite dev/build → 预览产物 → 完整退出。

### 应交付的代码

| 模块 | 最小职责 |
| --- | --- |
| `packages/cormi` | dev/build/preview 命令、配置入口、错误退出 |
| `packages/core` | 最小 Cordis 宿主、就绪检查和诊断，不依赖 React/Vite |
| `packages/builder` | 后端无关 BuildPlan/Builder/句柄契约 |
| `packages/plugin-web` | 应用编排、扩展点和受管生成 |
| `packages/plugin-vite` | Cordis provider，具体会话管理和 Vite 专属扩展 |
| React 插件 / React-Vite 桥接 / 默认 preset | 领域逻辑、后端集成和默认组合各有边界 |
| `packages/runtime` | Router、Provider 装配、mount/dispose |
| `examples/basic` | 真正通过公开接口运行的应用 |
| `tests/fixtures` | 独立项目根、路由冲突和配置错误等固定用例 |

没有真实职责的模块不先建空壳。引用源码继续保持独立，不参与 workspace 安装或发布。

### Basic 示例内容

示例包含首页、静态 about 页、带参数的 users 页面、公共 `_layout`、404/catch-all、一个局部 CSS 文件和公共静态资源。另加本地 status 插件：Node 部分贡献路由，浏览器部分贡献一个根 Provider。应用本身不通过内部路径访问框架。

显式 routes 与约定式 routes 各有一个 fixture。`base: '/demo/'` 的构建与深链接刷新必须单独验收；不能只在 `/` 首页证明“路由没问题”。默认请求代理作为配置透传验证，不在 P1 自研请求客户端。

### P1 退出条件

从没有 `.cormi` 的干净应用开始，dev 可以生成入口并打开页面；build 可以生成可部署静态产物；preview 不重新构建也能访问这些产物。配置错误、页面路径冲突、插件启动失败和 bundler 错误均退出非零，不能在日志打印 error 后继续报告成功。

构建产物不应出现 Cordis、Vite、Node 文件系统模块或私有环境变量。只做最小示例并不足够；上述成功与失败 fixture 必须随代码一同交付。

## 4. P2：开发态更新与故障恢复

先实现 revision、单消费者队列与旧结果丢弃，再接入页面增删事件；不要先靠一个 debounce 回调运行异步生成，然后在出现竞态后补丁式加锁。

每轮编译记录开始时的 revision、输入文件集合和贡献快照。编译期间出现新事件，旧轮可以结束计算，但不得提交；下一轮读取最新快照。相同入口 hash 不写文件、不触发额外刷新。生成临时文件不回流到页面扫描，页面源码和生成入口的 watcher 职责要明确分开。

Node 配置和本地插件源码更新采用 worker 重启。Supervisor 记录准确 worker 身份，等待旧实例释放端口；失败配置不能造成自动重启风暴。配置修复后能够重新启动，而无需用户手工清理残留进程。

### P2 退出条件

连续执行页面添加、删除、重命名、配置修改和插件修改后，浏览器显示最后一次有效输入对应的结果。过期编译不覆盖新结果，生成失败不破坏上次成功生成文件，重复重启不累积事件监听器和端口占用。

计划中的稳定性样本为至少 20 次启停和 100 组受控文件事件批次；这是测试要求，不是本次已测结果，也不是“100 次通过即可证明无泄漏”。更长时间运行应结合 watcher 数、句柄、子进程与内存趋势检查。

## 5. P3：类型、诊断、打包与最小发布准备

完成 `inspect` 与 `typecheck`，固定插件 ID、hook 排序、runtime 生命周期和配置 options 协议。为未冻结的 API 明确标记实验性，不为了宣布 1.0 而同时承诺所有设想。

`typecheck` 必须先 prepare，再调用所选 TypeScript 检查命令。CI 同时执行框架类型检查、单元测试、应用 build 和浏览器集成测试；单独 build 成功不足以替代 tsc。

使用实际打包产物创建临时消费者项目，测试 package exports、类型声明、CLI bin、ESM 导入与 peer 依赖。Workspace 链接能运行不证明发布包可用，必须从压缩包或等价安装形态验收。此阶段可以本地执行打包测试，不自动发布 npm 或推送远端。

最后选择一个小型真实应用进行试用，记录需要用户写多少配置、插件实际复用什么、错误诊断是否可理解。若只是相同 Vite 项目外多了一层配置，应该继续缩减设计，而不是用更多内置功能掩盖价值不清。

## 6. 完整测试矩阵

下表是完整测试规格；实际完成项以 P0/P1 实验记录为准，不能将整张表一并标为通过。

| 编号 | 场景与故障注入 | 预期断言 |
| --- | --- | --- |
| K01 | consumer 先于 provider 注册，provider 延迟激活 | consumer 只在依赖可用时运行；宿主屏障准确 |
| K02 | 必需 provider 永远缺失或初始化拒绝 | 有界失败，包含依赖链/原始 cause，无假启动成功 |
| K03 | 加载中 dispose，或父插件等待依赖自身服务的子插件 | 无悬挂任务；危险依赖组合明确失败 |
| K04 | consumer 清理被延迟，provider 同时卸载 | 资源有效期符合契约；最终端口和 watcher 全部释放 |
| K05 | 一个 disposer 抛错，另一个耗时 | 不遗漏剩余清理；退出报告 CLEANUP_INCOMPLETE |
| H01 | hook 同 ID、缺失 before 目标或循环顺序 | 报告冲突双方或完整环，不按随机顺序继续 |
| H02 | hook 在 await 后注销/追加，旧编译仍运行 | 当前快照不突变；仅下一轮看到新贡献 |
| G01 | 编译 A 等待期间发生 B/C 变更，A 最晚完成 | A 不提交，最终只使用最新有效 revision |
| G02 | 同一批输入重复触发，生成内容相同 | 不更新入口 mtime，不产生刷新循环 |
| G03 | 生成语法失败、磁盘写失败、提交前被取消 | 不覆盖上次成功入口，诊断保留失败原因 |
| G04 | 路径包含空格、Unicode、引号或符号链接 | 导入正确转义；越界写入被拒绝 |
| R01 | `[id]` 与 `[slug]` 结构歧义，文件与 index 冲突 | 构建前报告具体路径，不覆盖任何页面 |
| R02 | 多层布局、index、参数、catch-all 混合 | 匹配和 Provider/Outlet 层级正确 |
| R03 | 删除当前浏览页面，紧接着创建替代页面 | 更新后无旧 route ID、旧模块引用或无限重试 |
| D01 | `base: '/demo/'`，深路径直接打开与刷新 | HTML/JS/CSS 路径及 history fallback 一致 |
| D02 | 修改本地插件的传递依赖，而非入口文件 | 新 worker 使用新依赖代码，不复用旧 ESM 缓存 |
| D03 | 端口占用、重启中按 Ctrl+C、启动中失败 | 不误杀外部进程，不遗留自己创建的 worker |
| D04 | 配置持续报错后恢复为有效配置 | 无重启风暴，恢复路径明确且只启动一份实例 |
| B01 | React 页面正常但有 TS 类型错误 | typecheck 失败；不能以 build 转译成功掩盖 |
| B02 | 私有 env 与公开 env 同时存在 | 公开项可用，私有值不出现在客户端资产/manifest |
| B03 | runtime 从公共 barrel 间接 import Node 包 | 打包/依赖图检查失败，而非浏览器运行时报错 |
| B04 | 使用发布压缩包创建独立消费者应用 | bin、exports、types 和 peer 依赖均有效 |
| S01 | 两个 ProjectRuntime 使用不同配置并存 | 服务、路由、诊断互不串用；CLI dev/build 环境隔离 |
| S03 | 同一项目 dev 持锁时另启 build/typecheck，另一个项目同时构建 | 同项目写入被拒绝且不修改入口；不同项目不被错误串锁 |
| S02 | 20 次启停、100 批变更及延迟/失败混合 | 资源计数回落到基线，最后产物正确 |
| P01 | 独立消费者仅安装 core 及其运行依赖 | 无 Vite 模块也能启动、注入和销毁 |
| P02 | 同一 Web consumer 使用 fake builder 替换 Vite | 不修改消费代码，实际调用来自替换 provider |
| P03 | 重复 provider、缺少 vite 的专属桥接 | 明确依赖错误，不隐式重新安装 Vite |
| P04 | provider 启动中卸载，构建取消后迟到结果 | 不返回已失效会话，不把取消视为成功 |

测试应尽可能使用临时项目根和临时端口，测试结束后显式清理自身资源。必须有 timeout，使失败表现为可诊断断言，而不是 CI 一直挂着。涉及资源顺序时断言事件时间线，而不只对最后一个布尔值做判断。

## 7. 性能验证：先建立基线，再决定是否优化

初期不宣传“比 Umi 快”或“几乎零开销”。框架内核小，不等于应用构建快；功能范围不同也会让比较失真。

建立相同 Node、锁定依赖、硬件和页面集合下的裸 Vite 基线，分别使用 10、100、1000 个页面的合成 fixture，记录启动可服务时间、首个页面可交互时间、普通组件更新、路由结构更新、Node 配置重启和生产构建耗时。区分冷缓存与热缓存，重复多次后报告中位数及分位数，同时记录测量方式。

单独记录 Cormi 的扫描、hook、生成与写入耗时，才能判断额外成本来自哪一层。内存比较使用相同工作负载与运行时长，不拿 GC 前后两个任意时刻的 RSS 值断言泄漏。

优化触发应来自测量：扫描占比高才做增量索引；生成重复写入才优化 hash/缓存；配置重启确实成为瓶颈才研究 Node 插件细粒度 HMR。没有数据时不引入 MFSU、自研 bundler 或复杂缓存 DAG。

## 8. MVP 范围核对

| 范围 | MVP 状态目标 | 明确不承诺 |
| --- | --- | --- |
| 插件与 preset | Native Cordis 生命周期、可诊断依赖、内部嵌套 | 任意 Umi 插件直接运行 |
| 路由 | 小型约定式与显式配置、布局、动态参数、catch-all | 全量 Umi/Next/React Router Framework 语法兼容 |
| React runtime | 根 Provider、启动准备、路由通知、销毁 | 通用前端 DI 或跨应用微前端管理 |
| 构建 | 可替换 builder 契约，首个真实 provider 为 Vite | 第二个真实后端、跨后端插件自动兼容和自研构建加速 |
| 开发体验 | Fast Refresh、路由再生成、worker 重启、错误诊断 | 所有变化均无刷新、无停机、无状态丢失 |
| 配置 | 单入口、schema、mode、公开 env 边界 | 多层隐式配置与任意远程配置执行 |
| 质量 | typecheck、单元/集成/浏览器测试、发布包 smoke test | 只展示页面就视作完成 |
| 后续能力 | 在设计上保持边界 | SSR、SSG、RSC、微前端、插件市场已实现 |

Mock、请求、权限、国际化与 UI 库可作为后续第一批产品插件，不必强行全部进入底层内核。优先选择在实际试用应用中最频繁重复的一个功能，验证“可复用插件”价值。

## 9. 阶段停止与回退原则

若 P0 发现 Cordis RC 的关键生命周期与需求冲突，暂停对外冻结插件协议，先记录具体可复现失败。可在不同经过核验的版本之间做小规模对照，但不悄悄换回旧 API 后继续按 v4 文档宣传。

若插件 API 为了一个示例不断增加全局回调，说明分层还不清晰，应缩小 SDK 或把领域逻辑移回 preset。若为了复用 Umi 一段代码必须带入多个与目标无关的内部包，优先独立实现小的已知行为，而不是制造一份难以升级的半 Umi。

若路由变化 HMR 不稳定，退回明确的整页刷新；若 Node 模块热替换不稳定，保留 worker 重启。回退的是更新粒度，不是正确性和可诊断性。
